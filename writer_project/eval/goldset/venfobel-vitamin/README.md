# 골드셋 쿼리 작성 가이드 — venfobel-vitamin

## 목적

`gemini-embedding-001`(3072d)이 현 운영 모델 `text-multilingual-embedding-002`(768d)를
한국어 단문 retrieval에서 이기는지 사전 평가하기 위한 (쿼리, 정답 청크) 골드셋을 만든다.

이 골드셋의 품질이 평가 신뢰도의 상한선이다.

## 평가 설계 (참고)

운영 `_dual_retrieve`는 local store와 web store에서만 검색하고 score 머지 후 top-k 반환한다.
(통합 store는 `CHROMA_INCLUDE_BASE=False` 기본값으로 사용 안 함, `MERGE_RETRIEVE_MODE=web_first` 기본값.)

따라서 평가도 두 층위로 본다:

- **층위 1** (clean 신호): local 청크 안에서, web 청크 안에서 각각 ranking 평가.
  임베딩 모델 자체의 store-내부 품질만 깨끗이 측정.
- **층위 2** (운영 정렬): local + web 합친 통합 풀에서 ranking 평가.
  운영 `_dual_retrieve`가 머지 후 top-k 반환하는 시점과 정렬.

두 층위 다 한 번 임베딩하면 산출되므로 골드셋 작성 시 신경 쓸 것 없음.

## 작업 흐름

1. `chunks_sampled.jsonl` 을 VS Code 등으로 연다.
2. 각 줄은 한 청크. `text` 필드를 읽고, 어울리는 한국어 단문 쿼리를 `query` 필드에 입력한다.
3. **local 15~20개 + web 2개 (전부) = 총 17~22개**가 채워지면 충분.
   - venfobel 토픽은 web 청크 한계로 web=2개만 샘플링됨. 둘 다 query 채워야 tier2_merged 평가에서 web 기여가 살아남음.
   - local은 25개 다 채울 필요 없음. 자신 있는 것 15~20개가 25개 억지보다 평가 신뢰도 높음.
4. 애매한 청크는 `query` 빈 채로 둔다 — 평가 단계에서 자동 제외된다.

### 왜 store별 균형? — venfobel 토픽 특수 사정

**venfobel-vitamin은 web 청크가 8개뿐이고 길이/dedup 필터 후 골드셋에 2개만 샘플링됨.**
즉 본 토픽은 **tier1_web 평가가 구조적으로 불가능** (`MIN_QUERIES_PER_TIER=5` 미달).
평가는 다음 두 층위로만 진행:

- **tier1_local**: local 25개 청크 풀 안에서의 ranking. local 쿼리 5개 이상 채워야 살아남음.
- **tier2_merged**: local + web 27개 통합 풀에서의 ranking. 운영 `_dual_retrieve`와 정렬되는 본질 평가.

따라서 작성 우선순위:
1. **web 2개는 둘 다 query 작성** (tier2에서 web 기여 살리기 위함).
2. **local은 15~20개 자신 있는 것만** (tier1_local + tier2_merged 양쪽 동시 기여).

향후 web 인덱스 보강 후 재평가는 README-dev.md §12-N (별도 작업 큐) 참조.

## 작성 가이드라인

### 1) 단문 — 5~30자

운영에서 실제로 들어올 만한 검색어 길이.

- ✅ "벤포티아민 100mg 함량"
- ✅ "활성형 비타민B1 흡수율"
- ✅ "OTC 만성피로 표현 규제"
- ❌ "안녕하세요 제가 30대 직장인인데 요즘 너무 피곤해서 활성비타민을 찾고 있는데..." (너무 김)
- ❌ "비타민" (너무 짧음, 변별력 없음)

### 2) 자연스러운 검색어 톤 — 격식체 X

실제로 사람이 검색창에 칠 만한 표현.

- ✅ "벤포벨 임팩타민 차이"
- ✅ "이중제형 비타민 단점"
- ❌ "벤포벨S와 임팩타민의 차이점은 무엇인가요?" (격식체)
- ❌ "Q. 메코발라민 효능을 알려주세요." (질문 형식)

### 3) 청크 표현 베끼기 금지 — paraphrase

청크에 있는 단어를 그대로 옮기면 임베딩 유사도가 인위적으로 부풀려진다.
두 모델의 변별력 평가가 망가지므로 반드시 다른 표현으로 바꿀 것.

청크 예시: "벤포티아민은 비타민B1의 활성형으로 지용성이라 흡수율이 일반 티아민보다 높다."

- ❌ "벤포티아민 비타민B1 활성형 흡수율" (베끼기)
- ✅ "지용성 비타민B 흡수 잘되는 종류"
- ✅ "고함량 비타민B 종류"

### 4) 답이 청크에 *실제로* 있어야 함

추론으로 도달 가능하지만 청크에 직접 안 나오는 내용은 제외.
이건 retrieval 평가지 reasoning 평가가 아니다.

청크 예시: "벤포벨S는 만 19세 이상 성인 한정으로 용법이 표시되어 있다."

- ✅ "벤포벨 복용 연령 제한" (청크에 직접 있음)
- ❌ "임산부 벤포벨 복용해도 되나" (성인 한정→임산부 추론 필요, 청크 직접 언급 없음)

### 5) 애매하면 스킵

- 청크가 너무 일반적이라 어떤 쿼리든 매칭될 것 같으면 스킵
- 청크가 너무 specific해서 자연스러운 쿼리가 떠오르지 않으면 스킵
- 광고/추천 톤이 강해 정보 retrieval에 부적합하면 스킵

## 진행 팁

- **세션 나눠서 OK**: 한 번에 다 안 해도 된다. 10개씩 세 번 나눠도 됨.
- **VS Code 권장**: jsonl 한 줄이 길면 word wrap 켜기 (Alt+Z).
- **store 필드 신경 X**: 자동으로 박힌다. 너는 text만 보고 쿼리 작성.
- **확신 없는 쿼리는 작성하지 말 것**: 골드셋 노이즈가 평가 결과 노이즈로 직결된다.

## 진행 후

쿼리가 store별 15+ 개씩 채워지면 다음 명령으로 평가 실행:

```powershell
python tools/eval_embedding_models.py
```

결과는 `eval/results/venfobel-vitamin_gemini_vs_multilingual.md`에 저장된다.
